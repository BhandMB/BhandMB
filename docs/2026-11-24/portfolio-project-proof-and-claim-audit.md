# Portfolio Project Proof and Claim Audit

## Objective
Keep public portfolio claims aligned with verifiable repository evidence.

## Claim categories
- Implemented: source code and tests demonstrate the feature.
- Documented: a design note or README describes the intended behavior.
- Planned: work is not yet implemented.
- Verified: a repeatable test or deployment check provides evidence.

Do not describe a documented design as a shipped feature. Do not claim tests pass unless they were run against the current revision.

## Per-project evidence
For each featured project, link to the repository, setup instructions, architecture overview, representative API or UI evidence, and test commands. Identify known limitations honestly.

## Resume alignment
Use technologies only when they are present in the project or can be explained confidently in an interview. Separate hands-on implementation from fundamentals currently being learned.

## Maintenance cadence
Review pinned repositories, README setup steps, screenshots, dependency versions, and demo credentials before each major job application cycle.

## Final checklist
- Repository builds from documented instructions.
- Secrets and local database files are excluded.
- Demo credentials are clearly identified and safe for a local demo only.
- Screenshots match the current UI.
- Resume bullets are supported by code or test evidence.
